# РОЗДІЛ 1. АНАЛІТИЧНИЙ ОГЛЯД ПРЕДМЕТНОЇ ОБЛАСТІ ТА ПОСТАНОВКА ЗАДАЧІ ДОСЛІДЖЕННЯ

## 1.1. Інженерний реверс-скаутинг та технічні метрики існуючих рішень

У процесі системного дослідження було проаналізовано три програмні продукти-аналоги: Sally Face, Yandere Simulator та Doki Doki Literature Club Plus!.

### Sally Face
* **Архітектурний патерн:** Монолітна сценарна архітектура на базі рушія Unity зі статичним зв'язуванням через класи-менеджери (God Objects: GameManager, QuestManager).
* **Протоколи та взаємодія:** Локальна шина викликів Unity (SendMessage, делегати C#). Взаємодія з віртуальним девайсом реалізована через синхронне перемикання станів камери та Canvas.
* **Стек даних та персистентність:** Локальні конфігураційні файли (XML/JSON та PlayerPrefs) без валідації цілісності.
* **Критичні інженерні обмеження (Technical Bottlenecks):** Жорстке зв'язування графічного шару з логікою квестів; навантаження на Garbage Collector через постійне створення рядкових об'єктів.

### Yandere Simulator
* **Архітектурний патерн:** Монолітна спагеті-архітектура з використанням класів-богів (YandereScript, StudentScript) та багаторівневих ланцюгів if-else замість кінцевих автоматів.
* **Протоколи та взаємодія:** Пряме звернення через GetComponent() у щокадровому циклі Update() та публічні статичні поля.
* **Стек даних та персистентність:** Неструктурований PlayerPrefs без верифікації цілісності.
* **Критичні інженерні обмеження (Technical Bottlenecks):** Деградація продуктивності (CPU Bottleneck) через щокадрове опитування умов; неможливість модульного тестування; екстремальна зв'язність компонентів.

### Doki Doki Literature Club Plus!
* **Архітектурний патерн:** Дворівнева віртуалізована оболонка (Virtual OS Desktop), усередині якої функціонує скриптовий рушій новели.
* **Протоколи та взаємодія:** Внутрішньопроцесний IPC контракт передачі повідомлень.
* **Стек даних та персистентність:** Шифровані контейнери віртуальної ОС.
* **Критичні інженерні обмеження (Technical Bottlenecks):** Неможливість масштабування просторової взаємодії; надмірна витрата пам'яті (RAM Overhead).

## 1.3. Аналіз предметної області (Модель As-Is)

* **Ключові актори:** Гравець (Player), Неігрові персонажі (NPC), Тригери оточення (Environment Triggers).
* **Сутності даних:** InteractiveObject, QuestState, DialogueNode, SaveDataContainer, VirtualDeviceState.
* **Критичні дефекти As-Is:** Щокадрове опитування умов викликає CPU Bottlenecks; монолітні класи створюють High Coupling; відсутність валідації збережень викликає ризик пошкодження даних.

## 1.4. Постановка задачі та інженерні вимоги (Модель To-Be)

### Функціональні вимоги (Core Features)
1. **Contextual Interaction Module:** Автоматичне виявлення тригерів та виконання дій без віконного GUI.
2. **Narrative Graph Engine:** Обробка нелінійних діалогових графів із перевіркою булевих прапорців.
3. **Quest FSM Controller:** Керування життєвим циклом квестів на основі скінченних автоматів.
4. **NPC Behavior System:** Детерміновані стани неігрових персонажів через FSM.
5. **Virtual Terminal Subsystem:** Модуль віртуального пристрою з ізольованою логікою міні-ігор.
6. **Persistence Engine:** Збереження стану в JSON із розрахунком гешу SHA-256.

### Нефункціональні вимоги (NFRs)
* **Фреймрейт:** Стабільні 60 FPS ($\le 16.6$ мс на кадр).
* **Затримка (Latency p95):** Обробка подій в Event Bus $\le 5$ мс.
* **Пам'ять (GC Alloc):** $\le 10$ КБ на кадр у геймплейному циклі.
* **Час збереження:** Серіалізація $\le 50$ мс.
* **Цілісність даних:** Валідація за алгоритмом SHA-256.
* **Покриття тестами:** $\ge 75\%$ бізнес-логіки (Unity Test Framework).

### Постановка задачі
Таким чином, метою кваліфікаційної роботи є проєктування та розробка модульної клієнтської відеоігрової системи на базі подієво-орієнтованої архітектури та скінченних автоматів для рушія Unity, що забезпечує мінімізацію архітектурної зв'язності компонентів, виключення затримок обробки контекстних взаємодій (Latency $\le 5$ мс) та детерміноване збереження стану системи з валідацією цілісності.

## Висновки до розділу 1
У першому розділі виконано комплексний системний аналіз предметної області та існуючих архітектурних підходів. Дослідження індустріальних рішень (Sally Face, Yandere Simulator, DDLC Plus) довело застарілість монолітних структур і прямого опитування в Update(). Обґрунтовано доцільність впровадження Event Bus, FSM та ScriptableObjects. Сформовано функціональні та нефункціональні вимоги з індустріальними чисельними метриками. Отримані результати є вичерпним технічним завданням для проектування архітектури у Розділі 2.
